# Slipstream 0.1 Support and Release Contract

Slipstream 0.1 supports one Photographer who needs to review an existing Photo
Library without changing its Original Files. This document defines the support
boundary and the release notes for a separately approved `0.1.0` release. It
does not announce, create, or imply a tag or published release.

The product behavior remains authoritative in the linked Product and Design
Specs. This document defines which parts of that behavior an operator may rely
on in a 0.1 deployment.

## Supported Scope

A 0.1 deployment supports one Photographer and one configured local or
network-mounted Photo Library root. The server operator configures that root;
the browser cannot select arbitrary server paths. Original Files remain
read-only. The complete Library, Photo Set, Review, and Original ownership
rules are in [Photo Library and Photo Sets](photo-library.md) and [Review and
Selection](review-and-selection.md).

The supported deployment target is a Linux amd64 host running the
repository-owned Docker image and Compose configuration. The container is the
native dependency boundary: the Rust server uses LibRaw and libjpeg for RAW
embedded-JPEG extraction, and libvips with LittleCMS for JPEG normalization.
Bun builds the Web application and is not a production runtime dependency.

The supported network is loopback or one explicitly trusted private network.
Compose defaults to loopback. An operator may bind the published port to the
host's Tailscale address for Tailscale-only access. Tailscale binding does not
add Slipstream accounts or authorization. The service must not be exposed to
the public Internet, a public reverse proxy, or an untrusted LAN in 0.1.

Chromium is the supported browser target. Automated browser evidence runs
against Chromium and covers visible controls, keyboard operation, and touch
Pointer Events. That evidence does not establish support for Firefox, Safari,
or other WebKit browsers, and it does not substitute for a Photographer's
workflow acceptance on the intended device.

## File and Camera Boundary

Slipstream recognizes these extensions case-insensitively for discovery and
pairing:

- RAW: `3fr`, `ari`, `arw`, `bay`, `bmq`, `cap`, `cine`, `cr2`, `cr3`, `cs1`,
  `dc2`, `dcr`, `dng`, `drf`, `eip`, `erf`, `fff`, `gpr`, `iiq`, `k25`,
  `kc2`, `kdc`, `mdc`, `mef`, `mos`, `mrw`, `nef`, `nrw`, `obm`, `orf`,
  `pef`, `ptx`, `pxn`, `qtk`, `r3d`, `raf`, `raw`, `rdc`, `rw2`, `rwl`,
  `rwz`, `sr2`, `srf`, `srw`, and `x3f`.
- JPEG: `jpg` and `jpeg`.

Recognition means only that Slipstream indexes the file as a candidate RAW or
JPEG Original. It does not promise that every camera or every file with a
recognized extension can yield metadata or an embedded JPEG. LibRaw is the
container-support boundary for RAW files; unsupported, corrupt, or
resource-limited files remain unavailable rather than receiving a generic RAW
rendering.

`.ARW` is a recognized RAW extension. The actual-camera evidence boundary is
one opt-in local Sony ARW integration sample. It proves embedded-JPEG selection,
derivative dimensions, and unchanged Original bytes for that supplied sample
only. The repository does not contain that Original or treat the result as
evidence for every Sony body, every `.ARW` revision, or every LibRaw-supported
camera. A release qualification for a Photographer's library must use that
Photographer's representative Originals without adding them to the repository.

## Review Semantics

[Photo Previews](previews.md) defines Preview behavior. A matching JPEG
Original is the first Preview Source. When it is absent or unusable,
Slipstream uses the RAW Original's largest usable embedded JPEG. It does not
demosaic or develop RAW sensor data. The review surface identifies the source
and identifies limited detail when the source cannot support meaningful
magnification. A Preview failure does not alter an Original File or turn a
Photo into a different Photo.

[Photo Library and Photo Sets](photo-library.md) and
[Capture-Time Review Ordering](../design/capture-time-ordering.md) define
Capture Time. Filtered Photo Library Review orders by the authoritative,
camera-local Capture Time: valid RAW metadata first, then matching JPEG
metadata when RAW has no valid value. Timezone offsets remain metadata facts
and are not converted to UTC for ordering. Missing or invalid Capture Time
sorts in the deterministic missing-time partition. Photo Set membership order
is explicit and Capture Time never reorders it.

## State, Rescan, and Recovery

SQLite owns Photo identity, Photo Sets, Selection State, Rating, and saved
Photo Set progress. The state directory and derivative cache directory must be
separate from the configured Photo Library root. The supported writable schema
for 0.1 is SQLite schema version 3.

A rescan publishes one completed Library snapshot. It discovers new supported
files, refreshes changed files, marks missing files unavailable, and preserves
unaffected decisions and Photo Set positions. An unavailable Photo retains its
state and its last successfully inspected Capture Time. It becomes current
again only through a later scan of its available bytes; Slipstream does not
transfer its state to a replacement file. An active Review Session retains its
ordered Photo IDs while a rescan runs.

For a clean installation, use the repository-owned Docker procedure with a
canonical absolute Library root, a persistent state directory, and a separate
persistent cache directory. The initial scan completes before the service is
ready. The operator procedure, container hardening requirements, and health
boundary are in the [deployment guide](../deploy/README.md).

For an upgrade from schema version 2, stop the service and create a verified,
sidecar-free, consistent state backup before starting 0.1. The v2-to-v3
migration preserves existing durable records but has no in-place down
migration. To roll back across that migration, stop the 0.1 service and restore
the verified pre-upgrade backup before starting the earlier image. An earlier
binary must not be started against a newer schema.

A backup is accepted only after an isolated restore starts with the same
canonical read-only Library root and passes the documented state checks. The
cache contains rebuildable derivatives, not authoritative review state. An
isolated restore or a cache rebuild may use an empty cache directory; the
server regenerates derivatives on demand. Cache rebuild must preserve the
state database and must not modify Original Files. The detailed backup,
restore, and rollback procedure is in the [deployment guide](../deploy/README.md).

## Rollback Artifact Retention

A rollback artifact consists of the immediately preceding deployable image and
its compatible, verified state backup. An operator-controlled sealed rollback
archive, when retained outside the repository, is also a rollback artifact and
must remain independently accessible.

The minimum rollback window is 30 consecutive days after the replacement deployment passes production acceptance. A release approval may extend that window but must not shorten it.

An operator may retire a rollback artifact only after all of these conditions hold:

- the replacement deployment has passed its release acceptance and an isolated
  restore from its verified backup;
- the minimum or explicitly extended rollback window has ended;
- a tested rollback artifact exists for the then-current supported deployment;
  and
- no unresolved Original-safety, state-integrity, or service-recovery incident
  requires the artifact.

The release approval must identify the retained artifacts and the rollback
window. Source changes, a successful build, or a release-gate decision alone
do not retire an artifact.

## Known Limitations and Non-Goals

0.1 does not support multiple Photographers, accounts, authorization, public
Internet access, cloud backup, XMP or Original-file writes, AI selection, RAW
development, color-managed proofing, or parity with a desktop RAW editor. It
does not support arbitrary server-directory selection, continuous filesystem
watching, automatic move detection, full-resolution tiling, or an all-camera
compatibility promise.

The 0.1 browser reviews existing Photo Sets and the filtered Library. Photo Set creation, rename, deletion, membership, and explicit reordering are available through the trusted local HTTP API but do not yet have browser management controls. Filtered Library Review does not persist a resume position; durable progress belongs to Photo Set Review. Capture Time and metadata disagreements affect deterministic Library order but are not displayed on the Review surface.

Only the Linux amd64 Docker deployment and Chromium browser target are in the
0.1 support boundary. Direct host deployment, other CPU architectures, and
other browser engines may work but are not supported 0.1 release targets.

## 0.1.0 Release Notes

These are the notes to publish only with a separately approved `0.1.0` tag and
release action.

- Slipstream provides one-Photographer review of one existing Photo Library
  through a trusted-network browser deployment while keeping Original Files
  read-only.
- Matching JPEG Originals and RAW embedded JPEGs provide the Preview path;
  Preview source and detail limits remain visible instead of claiming a RAW
  development result.
- Filtered Library Review uses deterministic camera-local Capture Time order,
  while Photo Set order remains Photographer-defined.
- Durable Photo Sets, selection decisions, Ratings, and Photo Set progress
  survive restart, rescan, temporary file unavailability, backup, and
  isolated restore according to the linked specifications.
- Operators use the Docker deployment procedure, preserve a verified backup
  for schema upgrades, and may rebuild the derivative cache without losing
  durable review state.
- The limitations and rollback-artifact retention conditions in this document
  are part of the 0.1 support boundary.

Creating the tag, publishing release artifacts, and recording release-specific
image identity and acceptance evidence remain separate operator-approved
actions.
